## 2. 封包格式：OCArchive v3

### 2.1 结构

```
┌ 文件头 ─────────────────────────────────────────────────────────────────────┐
│ 0x000  u32            版本 = 3                                              │
│ 0x004  char[0x100]    包名（CP932，NUL 填充）"Hello_worldDVD"                │
│ 0x104  u32            K0 = 0xC8（加密类型标记；语料中恒定）                  │
│ 0x108  u32            hash0x89(包名) ^ 索引解压长度                          │
│ 0x10C  u32            hash0x89(包名) ^ 条目数                                │
│ 0x110  u32            K0 ^ 索引压缩长度                                      │
├ 索引区（0x114 起）──────────────────────────────────────────────────────────┤
│        zlib(索引)，CRC 头 78 9C；压缩等级 6 可逐字节复现                      │
├ 数据区 ─────────────────────────────────────────────────────────────────────┤
│        条目按索引顺序紧密排列，无填充                                        │
├ 尾部 ───────────────────────────────────────────────────────────────────────┤
│        固定 0x100000 字节（内容不定，原样保留）                              │
└────────────────────────────────────────────────────────────────────────────┘

索引 = 连续记录：
  [u32 name_len][name bytes(CP932)][u32 f0][u32 f1][u32 f2][u32 f3][u32 f4]
  key  = hash0x89(name)            ← 与条目一一对应，421/421 验证通过
  明文 = f_i XOR key  =>
        (数据区相对偏移, 原始大小, 本条索引结束偏移, 存储方式, 压缩大小)

hash0x89(s):  h = 0;  for c in s:  h = (h * 0x89 + signed(c)) & 0xFFFFFFFF
              （即 *137 + 有符号字节，来自 system.dll:0x406190 的机器码）

存储方式：
  1 = zlib 压缩（长度 = 压缩大小；数据即裸 zlib 流，无额外混淆）
  0 = 原样存储（长度 = 原始大小；**前 16 字节 = 明文 XOR (key 的 4 字节 LE 重复×4)**）
```

### 2.2 逆向过程（关键节点）

1. **头部扫描**：7 个 pak 结构与魔数一致（`03 00 00 00` + `Hello_worldDVD`），`0x114` 起为 zlib 流。
2. **发现“索引藏在数据里”**：`script.pak` 第 0 条解压后是 `[u32 名长][名][20 字节]` 记录序列，共 421 条，正好等于包内文件数 → 索引即第 0 条伪条目。
3. **索引字段疑似“被加密”**：20 字节 5 个 u32 在高 16 位上成组相同（如全为 `0x2025xxxx`），不合常理。
4. **用引擎代码定位解密器**：Ghidra 中 `FUN_004013F0`（读 5 个字段）→ 经由 `*DAT_00423AA8` 上的 “IEncryption” 对象 vtable（`0x41F790`）→ `0x406190` = `hash0x89`，`0x4060F0` = 逐字节 lane XOR。据此推测 “密钥 = 某字符串的 hash”。
5. **用文件魔数反推密钥流**：`system.pak` 第一条 `align.ini` 的密文 ^ 明文 `"[align0]\r\nalignX"` = `B1 71 25 20` 重复 4 次；`sound.pak`（OggS）、`cg.pak`（FFD8FFE0）、`mpeg.pak`（000001BA）、`data.pak`（`ViX ` + `\\Nitrofileserver\…`）全部对得上。
6. **确认密钥**：`key = hash0x89(条目名)`，`hash0x89("Hello_worldDVD") = 0x5327FC49` → 索引 5 字段、条目头 16 字节全部可用同一 key 解开；`0x108/0x10C/0x110` 三个头部字段也随之解开（解压长度 / 条目数 / 压缩长度）。
7. **全量交叉验证**：7 个 pak、34,953 条条目，偏移链 100% 连续、zlib 解压大小 100% 匹配、原样存储条目解混淆后 100% 得到合法文件魔数。

### 2.3 踩过的坑

* `0x110` 字段与真实的索引压缩长度差 4~440 字节不等 → 它是 `K0 ^ 压缩长度`，**不是**可以直接比较的尺寸。
* `data.pak` / `system.pak` 的数据区首部有 16 字节“乱码” → 不是文件头，而是**条目内容的头 16 字节被 XOR 混淆**（在 `align.ini` 上验证：解混淆后正是 `[align0]\r\nalignX`，正好 16 字节）。
* zlib 流可**逐字节复现**：Python `zlib.compress(data, 6)` 与原始压缩结果完全一致 → 重打包能做到 bit-perfect。

## 3. 脚本格式：`.nps`（CP932 文本标记语言）

### 3.1 行的四类语义

| 类型 | 说明 | 语料统计（46.8 万行） |
|---|---|---|
| 注释 | 行首 `//`（含 `//【角色】` 这类开发标记） | 64,611 |
| 命令 | 形如 `<TAG ATTR="V" …>`，可一行多条 | 208,812（纯命令）+ 1,235（HTML 残留） |
| **文本** | 直接显示的文字，可内嵌 `<K>` | 79,893（纯文本）+ 14,179（文本+记号） |
| 空行 | 仅排版 | 99,142 |

**文本行的界定**（提取/注入的唯一依据）：
`行内标签外的 // 之后为注释（不显示）` → `剔除 <…> 后的内容才是显示文本`。
例：`「もうっ！　うるさいな～っ！」//不機嫌` 显示部分只有引号内内容。

### 3.2 指令集（完整定义见 `tool/opcodelist.py`，含每条属性的必填性与取值域）

| 分类 | 指令 |
|---|---|
| 演出 | `BACKGROUND` `WIPE` `LAYER` `BUSTUP` `FACE` `SCROLL` `FLASH` `QUAKE` `IMG` `MOVIE`（+ 语料未用的 `BGANIM/BGMOVIE/ANIM/GLASS/CELL`） |
| 声音 | `SE`（4 声道）、`BGM`、`VOICE` |
| 流程 | `MARKER`（标签定义）、`A`（跳转/选项）、`CHOICE`、`SELECT`、`RETURN`、`CALL`、`END`、`LOAD`、`WAIT`、`ASYNCHRONOUS` |
| 系统 | `SYSTEM`（`timerclear/sceneChange/cgmode/ending/url/config/menu`…）、`CALC`、`SYSINFO`、`DISC` |
| 文本 | `BOX`、`CLEAR`、`HIDEMESSAGE`、`R`（注音）、`K`（消息内换行） |
| 预处理 | `INCLUDE`、`DEFINE`（文本替换）、`MACRO`（命令宏，`chara.h` 定义 `OPENSHUJINKOU_*` 等） |
| HTML 残留 | `HTML` `HEAD` `TITLE` `BODY` `PRE` `HR` `meta` `BIG` `B` |
| 行内记号 | `<K>`(8,284) `<k>`(26) `<Hidemessage>`(2) `<CLAER>`(14，**CLEAR 的错别字**，引擎应忽略) |

标签**大小写无关**（`<se>`/`<SE>`、`<clear>`/`<CLEAR>` 混用），小写形式占多数；`<>` 内为宏调用（如 `<コマンド 通常>`，由 `include.h` 的 `DEFINE` 展开）。

### 3.3 名牌（说话人）机制

* **`<VOICE NAME="角色名" CLASS="音声组" SRC="语音文件">`** —— 语料中 28,277 处；`SRC` 才是语音资源，`NAME` 即屏幕上名牌显示的字符串（如 `NAME="クラスメイト女３"`）。**译文写回时改 `NAME` 属性**。
* `<box name="圭介">`（`17_210.nps` 一处）—— 显式设名牌的写法，同样支持改写。
* `<BUSTUP NAME="…" BODY="…">` —— `NAME` 用于绑定立绘角色，**默认不改写**（避免破坏立绘查找）。
* `//【僕Ｍ】` 这类注释是开发者的说话人笔记，**不显示**，仅作为 `meta.json` 的 `dev_speaker` 参考。
* 语料共出现 **40+ 个名牌**（奈都美 11,833 / 薫 10,820 / 若佳菜 9,333 / 深佳 7,317 / 千絵梨 5,899 / 純子 3,548 / 遥香 3,132 / 都 / 佐知美 / 霧江 / エテコウ / そあら / ＨＩＫＡＲＩ / アルファ / みここ / キューちゃん / ハルカ / オシリス / ＳＨＩＯＲＩ …）。

## 4. 本地化约束

| 约束 | 说明与对策 |
|---|---|
| 编码 | CP932。简体字大多不在 CP932 内（`转/酱/问/测` 全部报错）→ 必须走**日繁字形映射**（如 `这→這、说→説、为→為、你→儞`，见备忘录）。工具对不可编码字符**报错并给出字符+位置**，不静默跳过 |
| 截断 | **不存在长度/偏移约束**（方案 B）：脚本是运行时解析的文本、跳转是符号引用。译文可任意长度，仅受屏幕排版影响 |
| 断行 | `system.ini [メッセージ]` + `backlog.ini` 提供**禁则表**（行首禁则 34 字、行尾禁则 17 字），引擎自身有自动换行；脚本另用 `<K>` 手动断行。工具提供 `--linebytes N`：按 cp932 字节断行 + 禁则处理 + 对话行行首补全角空格 |
| 字体 | `system.ini [メッセージ] fontName=ＭＳ Ｐゴシック`、`fontSize=20`；`backlog.ini` 同。**中文显示需改这两处字体名**（换成自制的 JIS 映射字体），文件在 `system.pak` 内 → 用 `pak_tool.py pack` 回写 |
| 排版 | `textbox.ini`：画面 800×600，`BOX0 = 720×195`（主要对话框，边距 10）、`BOX1..4` 为立绘对话框；`choice.ini` 选项框 580×40 |
| 名牌长度 | 名牌区域宽度有限，译名过长会溢出，请保持 ≤ 原文 2 倍字节数 |

## 5. 工具使用说明（`tool/`）

### 5.0 目录约定

```

├── tool\      pak_tool.py  opcodelist.py  nps_disasm.py  nps_asm.py  nps_text.py
├── unpack\    script\ （421 个脚本）  system\ （7 个 ini）  data\ （154 个资源）
```

### 5.1 `pak_tool.py` —— 封包（OCArchive v3）

```bash
python tool/pak_tool.py list   <pak> [--filter 关键字] [--limit N]   # 列表 + 结构自检
python tool/pak_tool.py unpack <pak> [-o 目录] [--only 关键字]        # 解包（生成 _order.txt / _pak_manifest.json）
python tool/pak_tool.py pack   <pak> <目录> [-o 新pak]                # 从目录重打包（同名文件覆盖，缺失沿用原内容）
python tool/pak_tool.py extract <pak> <包内路径> [-o 文件]            # 取单个文件
python tool/pak_tool.py verify <pak> [--mem]                        # unpack→pack→逐字节比对
```
* 拖放 `.pak` 到脚本上 = `unpack` 到同名目录。
* `pack` 会重算索引、偏移、头部三字段与条目头混淆，尾部 0x100000 原样保留。
* `--mem` 为纯内存往返（适合 `cg.pak`/`voice.pak` 这类 GB 级包）。
* 已验证：**7 个 pak 全部 bit-perfect**（`script.pak md5 4a610ce3009bfb99a67a663f327eb8f7` 等）。

### 5.2 `opcodelist.py` —— 指令集/操作码定义（唯一真值源）

* `OPCODES`：53 条标签的助记符、分类、语义、属性表（必填性 + 取值域 + 是否为显示文本）。
* `INLINE`：19 种行内记号；`NAME_SOURCE_TAGS`：名牌来源标签。
* `esc()/unesc()`：`.asm.txt` 的转义/占位符规范（`{{0D}}`/`{{09}}` 等，符合备忘录取向）。
* 自检：`python tool/opcodelist.py` 打印全表。

### 5.3 `nps_disasm.py` —— 反汇编（`.nps` → `.nps.asm.txt`）

```bash
python tool/nps_disasm.py <file.nps|目录> [-o 输出]      # 反汇编
python tool/nps_disasm.py --verify <file|目录>            # 反汇编→汇编→逐字节比对
```
输出 = **元信息头**（`.file/.encoding/.eol/.final_nl/.scene/.includes/.markers/.jumps/.choice/.names/.counts/.tags`）+ **逐行记录**：

```
L000016  TAG <se id="1" src="電覚活動開始2a" mode="fadein" time="" loop="off" effect="">
L000028  MIX 待機モードより通常モードへ移行<K>‥<K>‥<K>
L000507  TAG <voice NAME="奈都美" SRC="01_1\0000100">
```
* 六个行类型 `TAG/HTM/TXT/MIX/CMT/BLK`，负载为**原始行逐字节内容**；`Q` 型用于首尾带空白的行（引号+转义保存）。
* 标签使用**原文大小写**（`<se>` 与 `<SE>` 各保留），符号引用（`#标签`／`文件名`）直接以符号形式呈现。
* **零未知标签**：全语料 0 处未登记标签（`--strict` 时遇未知即退出）。
* 全量输出已生成：`work/asm/*.asm.txt`（420 个）。

### 5.4 `nps_asm.py` —— 汇编（`.nps.asm.txt` → `.nps`）

```bash
python tool/nps_asm.py <file.nps.asm.txt|目录> [-o 输出.nps]
```
* 剥掉类型前缀 → 按 `.eol`/`.final_nl` 还原；行号必须连续，否则报错中止。
* 验收：**420/420 逐字节零突变**（`--verify` 一键跑）。

### 5.5 `nps_text.py` —— 文本提取 / 写回（汉化主工具）

```bash
# 提取（默认：整行一条，行内 <K> 原样保留 = 无损）
python tool/nps_text.py extract unpack/script/script -o text/script
#   变体：--split-k（按 <K> 拆条）  --merge-k（合并整句，禁则留 meta）
#         --with-comments（连开发者注释一起提）  --keep-ascii（连纯 ASCII 也提）

# 写回
python tool/nps_text.py inject unpack/script/script text/script -o out/script \
       [--name-map names.json] [--linebytes 50] [--ini-dir unpack/system]

# 自检：未改动 JSON 写回必须与原文件逐字节一致
python tool/nps_text.py selftest unpack/script/script
```
* 输出严格遵循工程备忘录：`xxx.json`（`id → name → pre_jp → message`）+ `xxx.json.meta.json`（`line_no/kind/prefix/suffix/orig_span/name_line/name_tag/orig_name_raw/dev_speaker/…`）。
* 提取类别：`dialog`（有名牌）/ `narration` / `choice` / `ruby` / `calc` / `comment`（可选）。
* 名牌译文通过 `name` 字段写回 `<VOICE NAME="…">`（或 `<box name>`）。
* `--linebytes N`：按 cp932 字节断行，遵守 `system.ini` 禁则表，对话行补全角空格（无自动换行时的保险手段）。
* 编码校验：不可 CP932 编码的字符 → 报错 `译文无法用 cp932 编码: '转' (位置 4)  id=0`。
* 验收：**419/419 空注入逐字节一致**；实测改写 3 条 → 仅 3 行变化（含名牌改写 1 处）。

### 5.6 端到端作业流程

```bash
# ① 解包

# ② 反汇编（可读视图 + 结构核对）
```

## 10. 提取器缺陷修复与全量重审计（2026-09-17）

### 10.1 现象
实机测试时发现大量对白仍显示日文原文，密集旁白段约「两三句就漏一句」。

### 10.2 根因（两处，同源）
`nps_text.py` 的提取守卫写着：

```python
if s.startswith('<'):        # 行首是标签
    ...                      # 只扫名牌 <VOICE NAME=…>
    continue                 # ← 整行丢弃，正文永不提取
```

引擎把「消息内换行记号」`<K>` **写在下一行的行首**（语义 = 接续上一行并换行），
形如 `<K>身体器官保護に最適の状態を確認。`。这类行整体以 `<` 开头 → 被整行跳过。

之所以当初写成这样，是因为 `split_line()` 对行首标签同样有缺陷：它以「第一个非 `<>` 字符」
作正文起点，会把标签名本身（`K`、`se`…）当成正文（`<K>abc` → `K>abc`），只能靠整行跳过兜底。

### 10.3 影响面（独立审计，不依赖提取器自身判定）
* **漏提取 1,288 条**正文（其中 22 条为英文界面文本），涉及 **75 个文件**
* 单文件最多 `01_510.nps` 79 条；`01_100.nps` 69 条 / 原本 190 条 ≈ **26%**，与体感一致
* 同期确认「正确地未提取」的：纯标点/省略号行 `「‥‥‥‥」` `‥‥。` 等 **1,561 条**（无需翻译）

### 10.4 修复
1. `split_line()`：整段跳过**行首的完整标签序列**，再从剩余部分定位正文（顺带修正了
   `<R TEXT="…">正文</R>` 这类行首注音标签行的取文）。
2. `extract_file()`：删除「行首是标签就整行跳过」，改为「去掉标签后无可见文本才跳过」。
3. 新增 `is_text()`：含假名/汉字 → 提取；含拉丁字母且不是标签残片（排除 `N="right"…>`、
   `<DEFINE SRC=""…>` 这类解析残留）→ 提取；纯标点/纯数字 → 不提取。
   由此补上 `now connecting....`、`"MIKA" has joined chat-system.`、`「Ｈｅｌｌｏ、ｗｏｒｌｄ」` 等。

## 13. 遗漏选项定位与修复（2026-09-17 用户实机反馈）

### 13.1 现象
实机截图显示 `04_300.nps` 的两个选项仍是日文：
`深佳に声をかける` / `深佳に声をかけない`。

### 13.2 根因：属性名正则**区分大小写**
提取器里 choice / ruby 用的是 `re.search(r'\bTEXT\s*=\s*"([^"]*)"', …)`，**没有 `re.I`**。
而 `04_300.nps:155-156` 全库唯一地写成了**小写** `text=`：

```html
<CHOICE HREF="#声をかける" text="深佳に声をかける" OPERATOR="">
<CHOICE HREF="#声をかけない" text="深佳に声をかけない" OPERATOR="">
```

→ 这两个选项**从未被提取**，自然也没进待翻清单、没进 pak。

（同批排查：`\bNAME\s*=` 的小写写法 0 处；`OPERATOR` 正则本来就写了 `(OPERATOR|operator)`。）

### 13.3 修复与验证
* `nps_text.py`：choice / ruby 的 `TEXT` 正则补 `re.I`（顺带修好被兜底替换弄坏的 `m.group(2, re.I)`）。
* 空注入回归：419/419 逐字节一致。
* 重跑增量补漏：新增由 1,290 → **1,292**，补翻包新增 `04_300.json` 两条
  （`id=176 深佳に声をかける` / `id=177 深佳に声をかけない`）。
* 补翻（用词与 `19_970` 统一）：`向深佳搭話` / `不搭話` → 合并 → 注入 → 打包。
* 注入统计：382 文件 / 87,046 条，改写 86,795，**错误 0**，标签还原 68，标签冲突 20。
* **游戏目录 `script.pak` 已就地更新（4,228,785 B）**；验证
  `04_300.nps:155/156` 已是 `text="向深佳搭話"` / `text="不搭話"`。

### 13.4 结论：这类漏法已穷尽
全库扫描确认「小写属性名」仅此 2 处。加上此前修复的
`<K>` 行首、`<A HREF>` 显示文本、`<BUSTUP … ALIG` 折行残片、本轮的 `text=` 大小写，
**已知提取盲区全部关闭**。
