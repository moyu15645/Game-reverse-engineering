# LOVELESS 終わらない物語 —— 引擎分析与汉化工程报告

> 目标：`data.hed` / `data.dat` 归档格式、`.ovl` 脚本字节码 VM 的完整逆向，以及一套可复现的抽取 / 翻译 / 注入 / 封包工具链。
> 全部结论均来自对 `Game.exe` 的静态逆向（Ghidra MCP 反编译 + capstone 反汇编）与对 859 个脚本的实证统计。

## 1. 引擎概览

| 项目 | 结论 |
|---|---|
| 宿主程序 | `Game.exe`（397,312 字节，PE32 i386，Borland C++ 编译，TDB 调试段 `ffdff000`，时间戳 2000-09） |
| 子模块 | `DLL\hmc.dll`（启动时复制到 `%SYSTEM%`，提供 PSD/图形加载导出 `PSDLoadBlendedImage` 等） |
| 资源容器 | `DATA.HED`（索引，三重滚动 XOR 加密）+ `DATA.DAT`（裸拼接，不加密不压缩） |
| 脚本 | 859 个 `.ovl` 文件，自定义栈式字节码 VM，**未压缩、未加密**，Shift-JIS 明文 |
| 图形 | 193 `.psd` + 280 `.png` + 1 `.cur` |

| 配置 | `Game.ini`（`TITLE / FILEH / FILED / STARTSENARIO / MSDOS / CDROM / PATH` …） |

### 1.1 启动流程（顺带解决「不挂光盘就起不来」的问题）

`FUN_00404280` → `FUN_0040C480`：

1. 取当前目录 → `<cwd>\GAME.INI`
2. 读 `TITLE` 做**单实例检测**：`FindWindowA(NULL, TITLE)` —— 只要桌面存在标题恰为
   `TITLE`（默认 `LOVELESS`）的窗口就弹「２重起動防止」并 `exit(-1)`。
   ⚠️ 资源管理器文件夹窗口（`CabinetWClass`）的标题就是文件夹名，所以**打开名为
   `LOVELESS` 的文件夹再启动游戏必然误判**。
3. `GetDriveTypeA(cwd) == 5 (CDROM)` 或 `CDROM != 0` → **装机模式**：把数据复制到
   `<系统盘>\Program Files\<PATH>` 并从那里运行；否则**就地运行**。
   ⇒ 硬盘解压版本来就不需要光盘。
4. `CopyFileA(DLL\hmc.dll → %SYSTEM%\hmc.dll)` 后 `LoadLibrary`。

> 交付的 `Game.patched.exe` 只改了 1 个字节：文件偏移 `0x4341` 处 `74 JZ` → `EB JMP`，
> 无条件跳过上述误判分支。本汉化流程只改 `data.hed` / `data.dat`，**不会让该 exe 失效**。

## 2. 归档格式 `DATA.HED` + `DATA.DAT`

### 2.1 解密（`FUN_00402120`）

索引文件整体用**三重滚动 XOR** 加密，三条密钥各以 `\0` 结尾、**独立循环**：

```
keyB = "RIC"      (Game.exe .data 0x4520B4)
keyC = "VOICE"    (0x4520B8)
keyD = "SIDE-B"   (0x4520C0)
plain[i] = cipher[i] ^ keyB[i % 3] ^ keyC[i % 5] ^ keyD[i % 6]
```

### 2.2 明文布局（解密后）

```
偏移      长度      含义
0x0000    15        data.dat 的文件名（NUL 填充，实测 "data.dat"）
0x000F    2 (u16)   条目计数 count
0x0011    20*(count+1)  条目数组
```

单条 20 字节：

| 偏移 | 长度 | 含义 |
|---|---|---|
| +0x00 | 12 | 文件名（NUL 结尾，**尾部填充不一定是 0x00**，实测出现 `0x64`，必须原样保留） |
| +0x0C | 4 | 辅助字段 A（仅 6 种取值，与解包无关，原样保留） |
| +0x10 | 4 | **该文件在 data.dat 中的偏移 B** |

* 条目按 `B` 升序排列；文件大小 = **下一条的 B − 本条 B**。
* 最后一条是哨兵 `end`，其 `B` = `data.dat` 总长度。
* 实测：1396 条（1395 个真实文件 + 1 个哨兵），tiling 零缝隙，`0x11 + 1396×20 = 27937` 与文件长度精确吻合。

`DATA.DAT` 则是各文件原始字节的顺序拼接（开头即一张 PNG，无任何加密/压缩）。

> 工具：`tool/hed_tool.py`，`unpack` / `pack` / `list` / `verify`；**round-trip 已做到逐字节一致**（`data.hed`、`data.dat` 的 MD5 均与原文件相同）。

## 3. 脚本字节码 VM

### 3.1 解释器主体

`FUN_00410530` 是主循环：

```c
do {
    /* 1. 判定当前字节是「操作码」还是「文本」 */
    if (flags[b] & 0x0D) == 0 && (ctype[b] & 0x107) == 0 && b != ' '
        → 走 switch(*param_2) 分派操作码
    else
        → *local_338++ = b;   /* 累加进消息缓冲 local_230 */
    ...
} while (1);
```

* `DAT_00454D5E` 就是 **MSVCRT 的 `_ctype` 表**（`UPPER=1 LOWER=2 DIGIT=4 PUNCT=0x10 CTRL=0x20 …`），
  引擎直接复用它 ⇒ ASCII 字母/数字天然被当作文本。
* `DAT_00468EA1` 位于 `.data` 的 BSS 尾段（exe 文件里没有这段数据），由 CRT 在运行期初始化，
  静态无法读出；但它对文本/操作码的最终划分可以由 `_ctype` + 观测到的操作码集合唯一反推。

**每个主循环迭代开始时都会把累积的文本刷新到消息窗口**：`FUN_00420420(buf, &x, &y)`。
该函数是左对齐绘制 + 超宽自动折行：

```c
local_1a8 = FUN_00405f70(this, param_1, *param_2, *param_3, ...);   /* 返回绘出宽度 */
*param_2 += local_1a8;                                             /* X 游标前进 */
if (消息窗右边界 <= local_1a8 + *param_2) { ...按字符宽度切分... }   /* 自动折行 */
```

这一点是汉化方案的关键：**文本左对齐且自动折行 ⇒ 用半角空格补齐既不可见也不会多折一行。**

### 3.2 文本在脚本中的形态

实测一条典型对话：

```
0b 05 62 00 00 80 ff ff ff ff     EXPR sub05 : var[0x62] = -1
0b 04 33 00 00 80 62 00 00 80     EXPR sub04 : var[0x33] = var[0x62]
0b 38 cb 03                       EXPR sub38 : goto/调用 绝对偏移 0x03CB（文件头公共库）
82 a8 82 c9 81 63 ...             ← 文本区（CP932，示例「おに……ちゃん……」）
01                                MSGWAIT  ：消息结束、等待按键
0b 05 62 00 00 80 ffffffff        ...
```

* 文本 = 一段「非操作码字节」的连续区间；`0x0A`（NEWLINE）会在一条消息内部切成多个物理行，
  以 `0x01`（MSGWAIT）收束为一条逻辑消息。
* 统计：859 个脚本共 **1,218,983** 个文本区（含 1–3 字节的短碎片），
  归并成 **36,461 条逻辑消息**。

### 3.3 指令集

操作数只有三种读者（全部为**小端定长**）：

| 读取器 | 长度 | 语义 |
|---|---|---|
| `FUN_00414EE0` | 4 | **变量槽引用**：值必须形如 `0b10xxxxxx`（即 `(v & 0xC0000000)==0x80000000`），否则弹「フラグエラー / フラグを指定するところに定数が指定されています」。变量数组在 `this+0x1180`（2000 个 dword）。 |
| `FUN_00414E30` | 4 | **取值**：高 2 位为 `0b10` 时返回 `var[v & 0x3FFFFFFF]`，否则返回常量本身。 |
| `FUN_00414DE0` | 2 | 有符号 16 位立即数。 |

**顶层操作码**（`FUN_00410530` 的 switch，跳转表 `0x410F44`，19 项）：
`0x00 END`、`0x01 MSGWAIT`、`0x03/0x04/0x05 场景跳转/换脚本`、`0x06 场景命令子分发器`、
`0x08 刷新`、`0x09 等待`、`0x0A 换行`、`0x0B 算术 VM`、`0x0D/0x11/0x13/0x15/0x16 子分发器`、
`0x19 BREAK`、`0x23/0x24/0x25 内联标记`。

**`0x0B` 是引擎的算术/变量 VM**：`0x0B <subop:1> <操作数…>`，子操作码 **1..0x55（85 个）**，
跳转表 `0x419950`。已逐条提取每个子操作码的操作数布局（见 `tool/opcodelist.py::SUBOP_OPS`），
例如：

| subop | 布局 | 语义（已核对反汇编） |
|---|---|---|
| 0x01 | `flag4 val4` | `var[dst] += (int16)val` |
| 0x02 | `flag4 flag4` | `var[d] += var[s]` |
| 0x03 | `flag4 flag4` | `var[d] -= var[s]` |
| 0x04 | `flag4 flag4` | `var[d] = var[s]` |
| 0x05 | `flag4 val4` | `var[d] += val` |
| 0x25/0x27/0x2A/0x2B/0x2F/0x30 | `raw6` | 6 字节原样（标记 / 循环界定） |
| 0x26 | — | 向前扫描 `0b 25 00 00 00 00 FF FF` 标记并回跳（循环） |
| **0x32** | `flag4 s16` | **`if (var[f] > 0) goto 绝对偏移 T`** |
| **0x33** | `flag4 s16` | **`if (var[f] == 0) goto T`** |
| 0x34/0x35 | `flag4 s16` | 同上变体 |
| 0x36/0x38 | `s16` | 无条件跳转 `goto T`（状态 4，目标 = 脚本基址 + T） |
| 0x39 | `flag4 s16 s16` | 条件跳转 |

其他子分发器（跳转表已定位，项数已确认）：

| 顶层 opcode | 处理器 | 跳转表 | 项数 |
|---|---|---|---|
| `0x06` | `FUN_0041BCC0` | `0x41C8F0` | 22 |
| `0x0D` | `FUN_0041C950` | `0x41D492` | 15 |
| `0x11` | `FUN_00411470`（存档/读档/菜单/涂鸦板） | `0x414D3F` | 14 |
| `0x13` | `FUN_00419DA0`（绘图/调色板/滚动） | `0x41A7AB` | 24 |
| `0x15` | `FUN_00419B40`（精灵/图层绘制） | `0x41B054` | 25 |
| `0x16` | `FUN_0041D500` | `0x41E100` | 7 |

### 3.4 每个 `.ovl` 的公共结构

所有脚本的前 ~1800 字节是一段**近乎相同的公共库**（同一套文本显示/等待子程序）。
`0b 38 <T>` 的目标集合始终落在 `{4, 434, 922, 971, 1580, 1758}`，全部位于公共库内。
因此脚本区（文本所在）的改动**不会破坏这些向后跳转**——这正是定长替换方案安全的另一半原因。

## 4. 汉化方案：为什么选择「定长就地替换」

### 4.1 约束

脚本中存在**大量绝对 16 位偏移**指令（`0x0B` 子码 `0x32..0x39`）。一旦某条文本长度变化，
其后所有指令偏移平移，任何指向其后的跳转目标都会失效。
要做变长改写，必须掌握**每一个操作码的边界**才能建立 old→new 偏移映射；
而 `0x06/0x0D/0x11/0x13/0x15/0x16` 六组子分发器的操作数布局尚未全部逐条核对，
在这种前提下做变长重排风险不可控。

### 4.2 采用的方案

**保持每个物理文本区的字节长度不变，汉字用 SJIS 双字节写入，不足处用 `0x20`（半角空格）补齐。**

* 除文本字节外，脚本**一个字节都不动** ⇒ 偏移、跳转、标记全部原样 ⇒ VM 行为不可能改变。
* 绘制是左对齐 + 自动折行，补的空格在视觉上不可见，也不会造成额外折行
  （补齐字符宽度 ≤ 被替换的全角字符宽度）。
* 若某条译文超出原区长度，该条会被记入 `build/_overflow.json` 而**跳过不改**（保持原日文），
  绝不截断产生半句。

### 4.3 译文编码与映射表

1. 模型输出**简体中文**。
2. 按用户约定套用 `tool/hanzi2kanji_table.txt`（3019 条，`键<TAB>值` 单向**只应用一次**）：
   表内有的字换、没有的保持原字、映射表本身不修改。
3. 逐字 `encode('cp932')`；无法编码的字符（如音乐符号 ♪♫，本项目仅 1 例 `〞`）直接丢弃并记录到
   `build/unpack_cn/_dropped_chars.json`。

#### 关于映射表的实测结论（重要）

对全部 36,461 条译文做的统计：

| 指标 | 值 |
|---|---|
| 含至少 1 个 **cp932 不可编码字节**的消息 | 31,033 条（**85.1%**） |
| 不可编码字符的种类 / 出现次数 | 1004 种 / 115,704 次 |
| 高频不可编码字 | 这(5624) 么(4338) 吧(3614) 你(3496) 说(3451) 啊(2987) 样(2380) 吗(2253) 尔(2100) 们(2095) … |

也就是说：**简体字绝大多数不在 JIS X 0208 里，不套映射表会有 85% 的行缺字**，
所以这张表在本项目是**必需的**。

该表是**混用表**，条目分两类：

| 键 → 值 | 性质 |
|---|---|
| 说 → 説、时 → 時、们 → 們、这 → 這、尔 → 爾、异 → 異 | ✅ 常规「简体 → 日繁 / 日新字体」替换 |
| 你 → 凜、她 → 瑤、喂 → 鶫、啦 → 鼕、嗯 → 鶺、吵 → 鵐、吧 → 槇、吗 → 龜 | ✅ **字体槽分配**（含义见下） |

> **本表按约定视为权威表**：表内有的字按表替换、没有的保持原字、表本身不修改、单向**只应用一次**。
> 当前 `build/` 即严格按此规则生成。

#### 字体槽条目的含义（本作显示的前提）

「简体字绝大多数不在 JIS X 0208 里」是客观事实：实测 **31,033 / 36,461 = 85.1%** 的句子含
cp932 不可编码字节，所以这张表在本项目是**必需的**。

作者对**没有日文对应字形**的字（你 / 她 / 吧 / 吗 / 啊 / 呢 / 嗯 …）采用的是**字体槽**方案：
把它们安排到 `凜 / 瑤 / 鶫 / 鼕 / 鶺 …` 这些 **JIS X 0208 第 2 水準生僻字**的码位上，
再在**配套字体里把这些码位的字形重画**成对应的简体字。

* 判定规则（可用 `zhconv` 复现）：`zhconv.convert(值, 'zh-cn') != 原字` 且 值属 JIS 第 2 水準 → 字体槽条目。
* 全表 3019 条中，语料命中的有 **1018 种字 / 115,215 次**；其中
  **字体槽条目 248 种 / 24,358 次（21.1%）**，其余 630 种 / 70,723 次为常规简→日替换。
* 这些字体槽要正确显示，**需要配套字体**提供对应码位的字形。本作使用的是**系统 `ＭＳ ゴシック`**
  （取证：`CreateFontA` 调用点 VA `0x405fb6`，face 名 `ＭＳ ゴシック` @ VA `0x44c2f4`，
  `charset = 0x80` SHIFTJIS，且**无** `AddFontResourceA` ⇒ 游戏不自带字体）。
* 该问题**不能靠「不套映射表」绕开**——这些字本来就编不进 cp932，不套表会直接缺字，比显示错字更糟。

## 6. 交付物与使用

```
LOVELESS/
├─ Game.exe / Game.patched.exe     原始 / 去「２重起動防止」误判版（1 字节补丁）
├─ Game.ini  DATA.HED  DATA.DAT    原始游戏资源（未改动）
├─ tool/                           工具集（见上表）
│   └─ hanzi2kanji_table.txt       映射表副本
├─ unpack/                         DATA.HED/.DAT 解包产物（1395 个原始文件，含 859 个 .ovl）
├─ text/                           抽取的文本 JSON + meta（759 文件 / 36,461 条）
├─ trans/                          译文 JSON（message 字段）+ 翻译缓存
├─ build/                          重新封包产物（DATA.HED / DATA.DAT）与构建日志
├─ report/                         本报告 + 工具使用说明
└─ work/                           逆向过程脚本与中间产物（可清理）
```

### 完整复现命令

```bash
PY=tool/../envs/default/Scripts/python.exe      # 本机托管 Python

# 1) 解包
$PY tool/hed_tool.py unpack unpack/../data.hed unpack/../data.dat unpack

# 2) 反汇编（可选，用于审阅/手改）
$PY tool/disassembler.py unpack -o work/asm

# 3) 抽取文本
$PY tool/extract.py extract unpack text

# 4) 翻译（可中断续跑）
$PY tool/translate.py run --batch 200 --workers 6
$PY tool/translate.py apply

# 5) 注入（--map 启用 hanzi2kanji 映射）
$PY tool/extract.py inject unpack trans build/unpack_cn --map

# 6) 重新封包
$PY tool/hed_tool.py pack build/unpack_cn build/DATA.HED build/DATA.DAT
```

### 实机运行

把 `build/DATA.HED`、`build/DATA.DAT` 覆盖到游戏目录（记得备份原文件），
用 `Game.patched.exe`（或任意方式绕开标题误判）启动即可；**无需挂载镜像**。

## 7. 已知限制 / 未决项

1. `DAT_00468EA1` 分类表在 BSS，静态不可读。文本区边界用「`_ctype` + 观测到的操作码集合」
   反推，实测量级正确（提取出的对话通顺、无明显误切）；但理论上存在把操作数字节误判为
   文本的极端情形——已用「≥4 字节且含 ≥2 个双字节字符」过滤，且**注入只改这些区**，
   风险可控。
2. `0x06/0x0D/0x11/0x13/0x15/0x16` 六组子分发器的**子操作码操作数布局**未逐条核对
   （跳转表位置与项数已确认）。这是没有采用「变长重排」方案的原因。
3. 定长替换下译文受原区长度限制；超出者保持日文并记录在 `build/unpack_cn/_overflow.json`。
4. `hanzi2kanji_table.txt` 按约定为**权威表**：表内有的字按表替换、没有的保持原字、表本身不修改。
   其中约 21.1% 的命中属**字体槽条目**（你→凜 等），需要配套字体提供对应码位字形才能正确显示，
   详见 4.3。
5. 画面抓帧：游戏经 **DirectDraw** 呈现，`BitBlt` / `GetDIBits` 抓到的是全黑帧，
   自动化截图无法用于复核文本显示；实机复核对本作需**肉眼确认**（或用支持 DirectDraw 抓帧的工具）。
